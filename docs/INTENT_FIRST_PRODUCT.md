## 1. 文档目的

本文定义 FrameMind 如何将“先理清意图，再开始行动”落地为可交付、可验证的产品能力。

本文重点回答：

1. 用户提交需求后，FrameMind 如何判断意图是否足够清晰。
2. 什么时候应该提问，什么时候应该采用假设继续。
3. 如何让用户在 Agent 执行前确认目标、边界和验收标准。
4. 如何避免“Clarify”变成低效的连环追问。
5. 如何衡量 Intent-First 是否真正改善了任务结果。

---

## 2. 一句话定义

**FrameMind 在创建任务与执行任务之间增加一个可审计的 Intent Gate：先生成意图契约，必要时向用户提出少量关键问题，再由用户确认后开始执行。**

Intent-First 的核心不是“多问几个问题”，而是：

> 只在歧义会改变行动时提问；其他情况明确写出假设，让用户快速确认。

---

## 3. 要解决的问题

### 3.1 用户侧问题

传统 AI Agent 工作台存在三个典型失败模式：

1. **错误执行**：Agent 对模糊目标自行猜测，完成了一个用户并不想要的任务。
2. **过度确认**：Agent 反复追问低价值细节，用户需要写成长篇需求才能开始。
3. **执行后返工**：任务虽然“完成”，但交付物、边界或验收标准与用户预期不一致。

### 3.2 产品机会

FrameMind 不应与“更快的执行器”竞争，而应提供：

- 更少的无效执行；
- 更少的返工；
- 更早暴露风险；
- 可追溯的目标与约束；
- 对个人开发者、团队和企业都成立的治理能力。

### 3.3 成功标准

一次成功的 Intent-First 流程应满足：

- 用户能在一分钟内看懂 Agent 将做什么；
- 模糊任务不会直接进入沙箱；
- 清晰任务不会因为流程设计而明显变慢；
- 高风险动作在发生前被明确确认；
- 执行结果可以回溯到已确认的意图版本。

## 4. 产品原则

### 4.1 Clarity before action

执行前必须有已确认的意图契约，不允许只凭原始模糊指令直接创建沙箱。

### 4.2 Ask only when it changes action

问题必须影响下一步行动。不能影响行动的问题写入假设，不打断用户。

### 4.3 Facts before questions

能从代码仓库、已有文档、任务上下文自动获得的事实，不应反复询问用户。

### 4.4 User remains in control

Agent 可以建议目标、边界和验收标准，但最终执行授权属于用户。

### 4.5 Durable by default

澄清流程可以跨分钟、跨进程、跨天恢复。用户离开页面或 worker 重启后，任务状态不能丢失。

### 4.6 No silent assumptions on risk

低风险假设可以显式记录后继续；高风险假设必须由用户确认，或进入人工审批。

### 4.7 Progressive disclosure

界面先展示目标与交付物，再按需展开约束、假设、风险和执行细节，避免把复杂表单前置给用户。

## 5. 目标用户与核心场景

### 5.1 个人开发者

需要快速完成代码修改、文档整理、环境配置等任务，但不希望为每个任务编写完整需求文档。

关键诉求：

- 少填表；
- 先看到 Agent 的理解；
- 可以快速修改后执行；
- 零成本路径仍然可用。

### 5.2 团队

需要使用统一的任务边界、验收标准和审计记录，避免不同成员对 Agent 任务理解不一致。

关键诉求：

- 意图契约可共享；
- 高风险操作有确认和审计；
- 团队预算与权限可控。

### 5.3 企业

需要对生产环境、敏感数据、外部副作用和高成本任务进行更严格的意图与风险审查。

关键诉求：

- 强制执行高风险确认；
- 可审计的意图版本；
- 可配置的澄清与审批策略；
- 不在意图分析和沙箱中泄露凭证。

## 6. 核心产品概念

### 6.1 Intent Contract（意图契约）

Intent Contract 是用户与 FrameMind 在执行前达成的结构化共识。

```text
Intent Contract
├── goal                  最终要达成什么
├── deliverables          要交付什么
├── context               已知背景和事实
├── constraints           技术、时间、权限、风格等约束
├── non_goals             明确不做什么
├── assumptions           Agent 暂时采用的假设
├── acceptance_criteria   怎样算完成
├── risk_level            低 / 中 / 高风险
└── confidence            0-1
```

问题不放入 Contract，而属于 Intent Review。Contract 只表达当前已经理解或显式采用假设的内容。

Contract 必须满足：

- 用户可读；
- 可编辑；
- 每次修改产生新的 Intent Review 版本（`round`）；
- 可被审计；
- 执行必须引用某个已确认版本。

### 6.2 Intent Gate（意图闸门）

Intent Gate 是任务进入执行队列前的强制关卡。

只有以下条件同时满足，任务才可以进入 `queued`：

1. 不存在阻塞性问题；
2. 意图契约已生成；
3. 风险等级允许当前执行模式；
4. 用户已确认对应版本的契约。

### 6.3 Intent Review（意图评审）

一次 Intent Review 是 Agent 对当前任务和用户补充信息的结构化理解结果。

每次评审都产生新的 Review 版本，不覆盖历史版本。Review 包含：

- 当前意图契约；
- 是否需要提问；
- 问题列表；
- 决策类型；
- 风险等级；
- 置信度；
- 模型与成本信息。

### 6.4 Clarification Round（澄清轮次）

用户回答一次问题并触发一次重新评审，记为一轮澄清。

MVP 规则：

- 单次最多提出 3 个问题；
- 最多执行 2 轮自动澄清；
- 达到上限后不再自动追问，转为契约确认或人工处理。

## 7. 用户旅程

### 7.1 主流程

```text
用户描述任务
    ↓
FrameMind 分析意图
    ↓
┌───────────────────────────────┐
│ 是否存在会改变行动的阻塞问题？ │
└───────────────────────────────┘
        │是                         │否
        ▼                           ▼
展示最多 3 个关键问题         生成意图卡
        ↓                           ↓
用户回答                        用户查看 / 修改
        ↓                           ↓
重新分析                        确认并执行
        ↓                           ↓
最多 2 轮后生成意图卡          进入执行队列
```

### 7.2 清晰任务流程

示例：

> 将 README 中的 Windows 启动步骤改为 PowerShell 示例，不修改其他章节。

用户预期流程：

1. 提交任务；
2. 看到完整的意图卡；
3. 点击“确认并执行”；
4. 任务进入执行队列。

清晰任务不应出现无必要的问题。

### 7.3 模糊任务流程

示例：

> 帮我优化一下。

用户预期流程：

1. 任务进入 `awaiting_clarification`；
2. 展示少量关键问题，例如优化对象、优化目标、验收标准；
3. 用户回答；
4. Agent 生成意图卡；
5. 用户确认后执行。

### 7.4 高风险任务流程

示例：

> 删除数据库里的重复数据。

用户预期流程：

1. Agent 识别删除、数据库、不可逆操作等风险；
2. 提问或要求确认数据范围、判断标准、备份和回滚方式；
3. 意图卡明确标注高风险；
4. 用户确认契约；
5. 执行过程中仍可触发现有 `awaiting_approval` 人工审批。

### 7.5 用户离开后返回

澄清状态必须持久化。

用户次日重新打开任务时，应看到：

- 上次提出的问题；
- 已填写或未填写的答案；
- 当前意图契约版本；
- 任务仍停留在原状态，而不是丢失或自动执行。

## 8. 状态设计

| 状态 | 用户含义 | 是否占用执行并发 | 是否可创建沙箱 |
|---|---|---:|---:|
| `clarifying` | Agent 正在分析意图 | 否 | 否 |
| `awaiting_clarification` | 等待用户回答关键问题 | 否 | 否 |
| `awaiting_confirmation` | 意图卡已生成，等待用户确认 | 否 | 否 |
| `queued` | 已确认，等待执行 | 是 | 否 |
| `running` | 正在执行 | 是 | 是 |
| `awaiting_approval` | 执行中触发高风险动作，等待审批 | 是 | 是 |
| `completed` | 已完成 | 否 | 否 |
| `failed` | 执行失败 | 否 | 否 |
| `cancelled` | 用户取消 | 否 | 否 |

状态约束：

- `awaiting_clarification` 只允许进入 `clarifying` 或 `cancelled`。
- `awaiting_confirmation` 只允许进入 `queued` 或 `cancelled`。
- 未确认 Intent Review 的任务不能进入 `queued`。
- `awaiting_approval` 与 `awaiting_clarification` 不得混用。

## 9. 界面设计

### 9.1 任务创建区

输入仍以自由文本为主，不强制用户填写复杂表单。

建议文案：

```text
描述你想完成的事情
FrameMind 会先确认目标和边界，再开始执行。
```

输入框下方保留示例，但示例不应变成硬性模板。

主按钮建议从“提交”调整为：

```text
分析并继续
```

### 9.2 意图卡

意图卡是 Clarify / Align 的核心界面。

建议结构：

```text
我理解的目标
  将项目部署文档改为 Docker Compose 方式

交付物
  - 更新后的 README
  - 一份可执行的部署步骤

边界
  - 不修改数据库
  - 不调整生产环境配置

验收标准
  - 新开发者可以按文档完成启动
  - 命令可以直接复制执行

风险：中
待确认假设：
  - 使用现有 docker-compose.yml 作为基础

[修改意图] [补充信息] [确认并执行]
```

设计要求：

- 目标和交付物默认展开；
- 约束、假设、风险可以折叠；
- 用户可以直接编辑字段；
- 编辑后生成新版本；
- “确认并执行”必须明确显示将被确认的版本；
- 不允许在存在阻塞问题时直接执行。

### 9.3 问题卡片

每次最多展示 3 个问题。

每个问题包含：

- 问题本身；
- 为什么需要这个信息；
- 推荐选项；
- 自由输入；
- 可选“采用推荐假设”。

示例：

```text
你希望保留旧的部署方式吗？
为什么问：这会决定是新增说明还是直接替换现有章节。

○ 保留，新增 Docker Compose 方式（推荐）
○ 不保留，直接替换
○ 其他：________________
```

设计约束：

- 问题必须具体；
- 不使用“请补充更多信息”这类空泛提示；
- 不询问可从仓库自动发现的事实；
- 不重复询问用户已回答的问题；
- 用户无法回答时，应允许采用明确记录的假设；
- 高风险问题不能通过“采用假设”绕过确认。

### 9.4 执行前确认

确认按钮文案建议：

```text
确认意图并执行
```

确认后展示：

- 已确认的 Contract 版本；
- Agent 即将采用的执行范围；
- 风险提示；
- 可取消窗口或明确的取消入口。

MVP 不支持自动执行。即使任务非常清晰，也必须经过一次一键确认。

### 9.5 执行详情

任务开始后，执行详情页应保留意图卡，并显示：

- 当前确认版本；
- 执行中使用的主要约束；
- 子任务与父任务的关系；
- 高风险节点与审批记录；
- 最终结果对照验收标准的完成情况。

## 10. 澄清与判断策略

### 10.1 判断维度

Intent Reviewer 从四个维度检查：

| 维度 | 要回答的问题 |
|---|---|
| Actionability | 知道要做什么吗？ |
| Scope | 知道范围和边界吗？ |
| Verifiability | 知道怎样算完成吗？ |
| Safety | 是否涉及权限、凭证、外部副作用或不可逆操作？ |

### 10.2 问题是否阻塞

每个缺口必须分类为：

- `resolved`：已明确；
- `assumable`：可以采用安全默认值；
- `blocking`：不解决就会导致错误执行或高风险。

只有 `blocking` 才能生成问题。

### 10.3 决策类型

| 决策 | 条件 | 产品行为 |
|---|---|---|
| `ready` | 无阻塞问题，信息完整 | 生成意图卡，等待确认 |
| `confirm_with_assumptions` | 只有低风险可假设项 | 生成意图卡并展示假设 |
| `ask` | 存在阻塞问题且未超过澄清轮次 | 展示最多 3 个问题 |
| `manual_review` | 高风险且超过自动澄清上限 | 停止自动流程，要求人工确认 |

### 10.4 澄清上限

- 单轮最多 3 个问题；
- 最多 2 轮自动澄清；
- 第 2 轮后仍存在阻塞问题时：
  - 低/中风险：生成带假设的契约，要求用户确认；
  - 高风险：不允许自动执行，要求用户明确处理。

### 10.5 风险等级

| 风险 | 示例 | 默认行为 |
|---|---|---|
| 低 | 读取文件、生成文档、局部非破坏性修改 | 一键确认 |
| 中 | 修改多文件、改变接口、运行测试 | 展示影响范围后确认 |
| 高 | 删除数据、发布、支付、生产环境、凭证、外部副作用 | 强制风险确认，必要时人工审批 |

风险等级由规则和 Intent Reviewer 共同判断；高风险信号不能仅依赖 LLM 判断。

## 11. 多 Agent 使用原则

### 11.1 MVP 不采用多 Agent 投票

MVP 使用一个 Intent Reviewer 完成结构化审查。

不采用多个 Agent 对“是否清晰”投票，原因：

- 成本与延迟叠加；
- 多个同模型 Agent 的错误高度相关；
- 没有评测数据时，投票结果难以证明更可靠；
- 本地 Ollama 上会显著拖慢首次响应。

### 11.2 Context Scout

当任务关联代码仓库时，可增加只读 Context Scout：

- 读取仓库结构、README、AGENTS.md、依赖文件和相关代码；
- 自动补充事实；
- 输出 unresolved questions；
- 不修改文件、不接触凭证。

### 11.3 Risk Reviewer

Risk Reviewer 只在以下情况下启动：

- 涉及删除、发布、支付、生产环境、凭证或外部 API；
- Intent Reviewer 置信度低；
- 任务影响范围较大。

### 11.4 执行 Planner

执行 Planner 在意图确认之后运行，只负责：

- 如何拆解任务；
- 哪些步骤可以并行；
- 每个子任务的交付物与验收标准；
- 哪些子任务需要额外审批。

Planner 不得重新解释或缩小已确认的目标与约束。

## 12. 衡量指标

### 12.1 核心指标

| 指标 | 定义 | 目标方向 |
|---|---|---|
| 无效执行率 | 执行结果与确认意图不一致的任务比例 | 下降 |
| 返工率 | 执行后需要重新说明或重新执行的比例 | 下降 |
| 问题有效率 | 用户回答后实际改变契约的问题比例 | 上升 |
| 无效提问率 | 用户跳过或回答“无所谓”的问题比例 | 下降 |
| 平均澄清轮数 | 每个任务的平均澄清轮次 | 1 轮以内 |
| 契约修改率 | 用户在确认前修改契约的比例 | 用于校准理解质量 |
| 确认转化率 | 进入 `awaiting_confirmation` 后确认执行的比例 | 上升 |
| 首次执行成功率 | 确认后一次执行达到验收标准的比例 | 上升 |
| 首次行动时间 | 从提交到任务进入 `running` 的中位时间 | 清晰任务不明显恶化 |
| 风险拦截数 | 执行前识别并阻止的高风险任务数 | 可观测 |

### 12.2 质量评估集

MVP 后建立 30-50 条标注任务，覆盖：

- 明确低风险；
- 明确高风险；
- 目标缺失；
- 范围不清；
- 验收标准缺失；
- 可从仓库自动发现的信息；
- 恶意或提示注入输入；
- 多目标与冲突目标；
- 用户回答不完整；
- 超长上下文。

每条样本标注：

- 是否应该提问；
- 最多应问哪些问题；
- 哪些信息可以假设；
- 最低风险等级；
- 理想 Intent Contract。

## 13. MVP 范围

### 13.1 MVP 必须包含

- Intent Contract 数据模型；
- `clarifying` / `awaiting_clarification` / `awaiting_confirmation` 状态；
- 单次结构化 Intent Review；
- 最多 3 个问题、最多 2 轮澄清；
- 数据库持久化澄清会话；
- 用户确认门；
- 意图卡与问题卡前端；
- 未确认不创建沙箱；
- 审计记录；
- 多租户隔离测试；
- LLM 输出异常时的安全降级。

### 13.2 MVP 暂不包含

- 多 Agent 投票；
- 自动执行模式；
- 完整 Context Scout；
- 自动仓库索引；
- 多模型路由与模型竞赛；
- 团队级意图模板市场；
- 自动评测平台；
- 跨任务学习用户偏好。

---

## 14. 发布验收标准

满足以下条件才可发布 MVP：

1. 模糊任务不会直接进入 `queued` 或创建沙箱。
2. 清晰任务能生成意图卡并一键确认执行。
3. 用户回答后可以触发新一轮评审。
4. 单轮问题数不超过 3。
5. 自动澄清不超过 2 轮。
6. 未确认或版本过期的意图不能执行。
7. 高风险任务不能通过“采用假设”绕过确认。
8. 用户离开后返回，任务状态与问题仍然存在。
9. 不同租户无法读取彼此的意图契约。
10. 每次确认、修改、执行都可以追溯。
11. 本地 Ollama 配置下仍可完成完整流程。
12. 模型输出非法结构时不会导致任务被自动执行。

## 15. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 过度澄清 | 用户觉得比直接执行更慢 | 只问 blocking 问题；最多 2 轮 |
| 澄清不足 | 仍然执行错误任务 | 用验收标准与风险检查兜底 |
| 本地模型 JSON 不稳定 | 无法生成契约 | Pydantic 校验、一次修复重试、安全降级 |
| 用户不看意图卡 | 确认流于形式 | 突出目标、交付物、风险与假设 |
| 高风险判断漏检 | 不可逆操作被放行 | 规则 + LLM 双重判断；高风险强制确认 |
| 上下文泄露 | 仓库信息进入不合适的模型 | 明确模型边界、敏感信息过滤、凭证不进入上下文 |
| 状态过多 | 工程复杂度上升 | 意图状态与执行审批状态严格分离 |
| 成本增加 | 零成本路径变慢 | 单次评审优先，条件性启用第二 Agent |

## 16. 后续路线

### 阶段 1：Intent Gate MVP

完成意图契约、澄清循环、确认门和前端交互。

### 阶段 2：Context-aware Clarification

接入只读 Context Scout，减少可以从代码仓库回答的问题。

### 阶段 3：Risk-aware Review

对高风险任务启用 Risk Reviewer 和更强的审批策略。

### 阶段 4：Evaluation

建立意图理解评测集，持续优化问题生成、假设质量和执行成功率。

## 17. 产品决策记录

### 已决定

- MVP 默认始终展示意图契约并要求用户确认。
- MVP 不使用多个 Agent 投票判断清晰度。
- 澄清状态持久化在数据库，不依赖长时间 LangGraph interrupt。
- `awaiting_clarification` 与 `awaiting_approval` 是不同状态。
- 高风险任务不允许通过默认假设直接执行。

### 待后续验证

- 是否提供 Fast 模式，让高置信度低风险任务跳过人工确认。
- 是否允许团队配置“必须确认”的字段。
- Context Scout 何时读取仓库、读取哪些路径。
- 用户偏好和团队策略是否影响澄清问题数量。
